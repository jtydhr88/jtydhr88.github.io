如何使用AI逆向一款游戏

Terry · 2026-10-05

首先，写在最前面，出于对这款游戏（以及我自己）的保护，我是不会提供任何关于这款游戏的信息或是截图的。

其次，标题里与其说是“使用AI”，倒不如说是“观摩AI”，全程我自己没做什么技术指导，基本上就是提需求。

但是在前AI的年代，因为我自己对这款游戏做过一定程度的逆向分析，所以AI做的大致方向我还是懂一些的。

写这篇观摩AI的文章的初衷更多是感慨，以前那些日日夜夜的研究，几天的功夫可能才达到30%，但是现在AI几乎2个小时就做到了80%，唏嘘不已。

同时我不会回答任何类似的问题：

  • “这是什么游戏？”
  • “能不能用在其他游戏上？”
  • “我的AI为什么不行？”

更不可能“帮我也搞下呗，付费也行”这样的。

本文仅作技术分享，抛砖引玉，请使用你的AI进行验证。

Part 00

环境

  • 游戏：某手机游戏安卓版
  • 运行环境：某安卓模拟器
  • 游戏引擎：Unity定制版
  • AI：Claude Opus 5.5
  • 操作系统：Windows 10

同时因为我本来就是开发者，所以本机已经装了很多开发类的工具，比如：

Java，nodejs，python，VS等，在后面的AI逆向过程中，我看到他们都被用到了。

Part 01

提取资源

这其实是我最开始的目的，我本来就是想试一试如何用AI提取一下，以前提过的这个游戏。

当我和AI提出这个需求的时候，我只把模拟器的路径给了它，结果它自己调用了工具，列出来了模拟器中占用最大的那个，就是我想要的那个。

待补截图AI 列出模拟器里占用最大的那个，就是要提取的游戏

这里面有一个前置条件，是我提前进入到了游戏在游戏中把全部资源下载了下来。

和AI这么说的时候，AI自己把安装包和资源包一起找到，并提了出来。

这里有一个小插曲，因为全部的资源过大，将近40个G，我中间自己还把模拟器给停掉了，后面又续上了。

Part 02

解包资源

到这一步，其实以前在手工的时代，我自己都做过，网上还有针对这个游戏的教程，但是教程是针对老版本的，在游戏某个大版本之后，这个教程里的步骤就不好使了，包括里面的一些技巧。

但我还是把这篇教程给了AI，让AI参考着来，这时AI展示了高超的逆向本领：它先是对比了文件头，发现新版本只是在每个资源文件前面垫了 8 个字节的 0，后面就是完完整整的标准的资源包，跳过这 8 个字节，现成的解包库就能直接读；然后发现资源分散在两处，安装包自带一份，游戏运行后又下载了一份更新，要按“更新覆盖原版”合起来才是完整的一套；连从模拟器拉文件都踩了个坑：Windows 下 adb pull 遇到中文文件名会出错，它改成在手机端打 tar 包、流式传回来再解开。最终成功地把资源提取了出来。

Part 03

资源映射

从这里开始就是以前手动很麻烦的步骤，因为游戏中看到的都是名字，但是提取的资源使用的都是编号，于是我让AI去找一下在逆向出来的代码哪里存放了它们真实的名字。这是以前从来没有做到的。

这时AI找到了它的加密数据库，分析出来它的加密算法，然后把数据库给解开了，整个游戏的资源映射关系就被它这样找到了。

待补截图解开的数据库和资源映射

它先注意到配置目录里有一批文件大小整齐、但打不开的数据库，逐字节比对后发现只是做了一层异或：0 字节和等于密钥的字节会原样跳过，连 SQLite 文件头里的页大小字段都被搅乱了，把这些还原之后就是普通的 SQLite，每条记录的值是一个前缀字节加一段 JSON；然后发现名字和描述在数据库里，但编号、类型这些另一半字段藏在 Lua 字节码的配置表里，它又写了个 Lua 字节码的读取工具把这一半也读了出来；最后按编号把两边拼起来，生成了一份“名字 → 编号 → 资源文件”的中文索引表，想看哪件东西直接按名字搜。

这是已经比我手动的年代提高了一大部分。

Part 04

材质，贴图，Shader

从这里开始，其实就是之前没有做过的了，这一次也让AI开始做，就是把这个游戏的材质，贴图，甚至是shader试着看看能不能给应用到导出的模型，答案是能，而且做得非常好，后面几乎所有的逆向都是以这一步作为基础去做的。

它先在资源包的 Shader 对象里找到了游戏自带的、已经编译成 GLSL 的着色器代码。这些代码被一种自定义的分块格式压缩打包，一个 Shader 里有成百上千个变体，它解开之后，按材质上开的关键字挑出对应的那一个。然后它在网页里用 three.js 直接跑游戏的原版 GLSL：把 Unity 风格的 GLSL 转成 three.js 能编译的写法，把引擎每帧往 shader 里塞的全局参数（相机矩阵、主光、球谐环境光、阴影图等）按同样的名字补上，混合、剔除、深度写入这些渲染状态也照每个 pass 的设置来。最后是一个个坑地对齐画面：

  • Unity 是左手坐标系，镜像到 three.js 之后三角形绕序要翻过来；
  • 一个材质有好几个 pass 叠着画，要按层全画上；
  • 游戏是线性色彩空间，材质里的颜色要先从 sRGB 转成线性；
  • 阴影矩阵没设的时候全是 0，shader 里除以 0 出 NaN，整块发黑；
  • 某些顶点数据是 16 位整数存的，要先归一化。

因为我自己做开发的时候也需要用到glsl代码，我开始认真对待起来。

Part 05

骨骼，蒙皮，动画

因为这个游戏自带了很多动作，还有动画，既然做到了这一步，那我接下来就想试一试，能不能把里面大量的动画给应用上来，同样的，没有问题。

它先发现动画曲线是压缩过的，暂时解不开，但每个片段里另外存了首帧和末帧的原始值。骨骼对应关系是按“骨骼路径的 CRC32 哈希”存的，它逐个算路径哈希对上骨骼，先用首帧把两千多个静态姿势还原了出来。

然后它把模型蒙皮挂到骨骼上。权重有的存成 16 位整数，有的只存了骨骼下标，都要统一归一化。模型由多个部件拼成，每个部件按“占哪个槽位、要隐藏哪些槽位”的规则决定显示哪些网格。有的部件是在另一套绑定姿势下做的，得把相关网格按那套绑定姿势重新蒙皮，再用一层叠加动画做微调。

最后是完整动画。它认出这种压缩格式就是开源的 ACL（Animation Compression Library），还对上了具体版本。拉下官方源码编成 DLL 给 Python 调，再把解出来的曲线对回骨骼；本地服务按需解码并缓存。同名的镜头片段也一起解出来，跟角色动作同步播放。

在做这步的时候，AI找到了压缩格式，然后自己下载源码、写好编译脚本，用我本机装的 MSVC 2019 Build Tools 编译了出来。

Part 06

镜头，运镜，场景，道具

因为游戏中有拍照的功能，所以说接下来我让它把镜头运镜相关的代码也给逆向了出来并添加了进去。

同时补上了场景以及道具相关的。

它先从镜头下手：

  • 动作和镜头动画是同名成对存放的，镜头动画是没压缩的曲线，记着镜头的位置、朝向和视角。Unity 是左手坐标系，搬到 three.js 要把位置的 x、四元数的 y 和 z 取反。
  • 过场用的 Timeline 被拆成了很多小包，它把里面 Cinemachine 的虚拟镜头（跟随点、看向点、视角、侧倾）逐帧算成普通镜头。
  • 真正的时间安排写在 Lua 字节码的时间轴配置里，它用符号执行把每段的起止帧和挂点读了出来。
  • 拍照镜头是几档预设按缩放程度插值出来的，也照着还原了。

然后是场景：

  • 环境预制体、光照贴图（每个渲染器各自的索引和缩放偏移）、光照探针（四面体重心插值）、平面反射，都按引擎的做法接上了。
  • 运行时生成的海面是逆向引擎代码还原的：网格没有顶点数据，靠 gl_VertexID 在 shader 里算位置，浪由一批“波粒子”画进贴图。
  • 用顶点动画贴图驱动的场景动画也接上了。

最后是道具：

  • 配置表写着“哪个动作把哪个预制体挂到哪根骨骼上”，道具有自己的骨骼和动画，动画用的是 Unity 标准的曲线格式，带显隐曲线。
Part 07

粒子特效

然后，就是质的飞跃，粒子特效。

本来我也没有想到可以做到这一步，但是AI自己说还没有做的时候，我就问了它一句是不是可以去做，然后它做了简单的调查后，说可以，接着就给做出来了，同样的是把游戏里等价的源码给逆向了出来。

它先解决了读取的问题：粒子系统的序列化格式被改过，头部多了一个模块掩码，只有掩码里标了的模块才会完整写入，其余模块只剩一个开关位。现成的解包库照标准格式读，会直接读越界。它摸清规则后自己写了读取器，一千七百多个粒子系统全部读对。

然后在浏览器里重写了模拟：发射、各种发射形状、随生命周期变化的速度 / 大小 / 颜色、序列帧、子发射器、拖尾都做了。粒子数据按引擎的顶点流规则打包，直接喂给游戏自己的特效 shader。

最后是逐点对齐：像噪声这种公开资料写不清楚的模块，它直接反汇编引擎的二进制，用 CPU 模拟器跑原函数，和自己的实现对拍，直到输出一模一样。

到这一步，才过去不到一个小时。

当把粒子特效实现进去的时候，整个游戏的效果已经和我在游戏里看到的几乎一模一样了。

Part 08

碰撞，布料模拟

我以为这就到头了，我以为接下来这些在外部端就做不了了。我这么问 AI 的时候，它一开始并没有直接说可以做，而是给了两个选项：第一个是做一个近似的，第二个是完全逆向出游戏本身的源码。我就直接让它按第二个做了，然后它就做出来了。

它先找到了物理参数：每个部件的物理配置存在一个资源文件里，全局还有一套身体碰撞胶囊和驱动骨骼。然后它去啃求解器：游戏的物理跑在 Unity 的 Burst 编译代码里，这个库带着完整的符号表，它用 Ghidra 批量反编译；C# 那一层是 IL2CPP，元数据文件被混淆过，现成的 Il2CppDumper 用不了，它自己写了一个 dumper 解开。最后按反编译结果用 JS 重写了一遍求解器，函数名和游戏里一一对应，包括：

  • 固定子步长和两种积分方式；
  • 刚度、弯曲、长度约束；
  • 带噪声的风；
  • 粒子和胶囊、平面、网格的碰撞；
Part 09

灯光

做到这步，应该没什么能难住它的了。我问它还有什么没做，它说还有灯光，那我说好，把灯光也做了吧。

它先找到了灯光数据的真正来源：资源里有一套旧的灯光资源文件，但游戏实际用的是另一套写在 Lua 字节码配置里的灯光预设。它用自己写的 Lua 反汇编器把这些预设读了出来。

然后是换算：它对着逆向出来的代码，把每个预设里的主光、角色补光、球谐环境光、反射球，逐项换算成 shader 里对应的全局参数。颜色要按线性色彩空间处理，球谐系数要从引擎内部格式重新打包。过场动画里每个镜头换一套灯，时间也从时间轴配置里读。

最后是后期：游戏用的是 URP 的后期体积，但后期 shader 不在资源包里，而是藏在安装包的引擎数据里，而且没有类型信息。它借资源包里 Shader 对象的类型定义把它们读了出来，于是 Bloom、调色 LUT、色调映射这些都直接跑游戏的原版代码，参数换算也对着反编译的 C# 一项项核过。

Part 10

其他细节

到此为止，我相信只要我想，我可以让AI把这个游戏里面全部的内容都扒出来。比如后来我们又陆续做了：

  • 屏幕空间次表面散射；
  • 近景阴影和自发光；
  • 眨眼和“看镜头”；
  • 跟着动作走的模型显隐；
  • 场景雾和背景视差；
  • 配乐和音效；
  • 场景实时灯和渲染层过滤；
  • 最后把蒙皮从 CPU 挪到 GPU，重场景从十几帧提到了 60 帧。

这些细节。
